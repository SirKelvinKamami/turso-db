# Lessons — Webhooks on turso-service (2026-08-29)

## Fire-and-forget webhooks must not block the write response
Dispatch via `tokio::spawn` per hook. Keep the commit/response hot path synchronous
and kick delivery to a background task, otherwise one slow receiver makes every
`/execute` wait. Give the client a 10s timeout so a hung receiver never leaks a task.
Verified: a 2-statement batch returned in ~114ms while delivering in the background.

## Sign webhook bodies, not just tokens
`X-Turso-Signature: sha256=<hex HMAC-SHA256 of the raw request body>` lets receivers
verify authenticity+integrity when a shared `secret` is configured. HMAC-verify with
a constant-time compare on the receiver (not visible to the sender-side).
RFC 2202 vector for `hmac("key", "The quick brown fox jumps over the lazy dog")` is
`f7bc83f430538424b13298e6aa6fb143ef4d59a14946175997479dbc2d1a3cd8` — a great unit test.

## Classify reads vs writes BEFORE running SQL
`splitting SQL on `;` gives statement strings; a first-keyword classifier
(select/with/pragma/explain/values = read-only) decides whether something is a write
without executing. Keeps webhooks from firing on SELECTs routed through the same execute
path. Shared helper (`sql_is_query`) avoids divergence between REST and pipeline.

## Projection: report what was intended, not measured
After execute, only `rows_affected` + the SQL text are cheaply available — not which
rows/columns actually changed. For MVP the payload lists `statements` + `rows_affected`;
true change capture (row-level) needs SQL analysis or a change-tracking layer framing
BEFORE execution. State that limitation explicitly rather than implying row-level detail.

## axum handler extractor order
`Bytes` (request-body extractor) must come AFTER `HeaderMap`/`State` (immaterial
extractors) in the handler signature; put any body-consumer last. Getting this wrong
produces a confusing `Handler`-trait error in tests that spin up an in-process router.

## Persist config-like state to a file following the app's existing pattern
Webhooks file lives alongside the DB manifest (`DATA_DIR/webhooks.json`), matching the
walk-and-save approach used by `DatabaseManager`. It surfaced naturally in the smoke
test that deleting a DB must also clean its webhooks (else stale file entries linger).
